# UO0001: Unsupported EF Core SQL translation

Category: `UO.Reliability`. Default severity: **Warning**, enabled by default after explicit profile configuration.
Location: the entire unsupported invocation. No Code Fix or suppressor is provided.

The rule catches row-dependent overloads that have no built-in translation in a selected provider snapshot.
It is independent of CA1862, which can suggest comparisons that do not translate in EF queries
([upstream issue](https://github.com/dotnet/roslyn-analyzers/issues/7141)).

## Configuration

**Package installation and `severity = warning` alone are not enough.** Select a recognized provider
profile, then opt in any files whose EF query sources are opaque `IQueryable<T>` abstractions.
Place these options in the consuming project's `.editorconfig`:

```ini
[*.cs]
dotnet_code_quality.UO0001.ef_core_providers = npgsql-8.0.0, sqlite-8.0.0
dotnet_diagnostic.UO0001.severity = warning

[**/CustomerQueryHelpers.cs]
dotnet_code_quality.UO0001.assume_ef_core_queryable = true
```

Replace `CustomerQueryHelpers.cs` with the actual filename containing your query helpers.
The `8.0.0` suffix identifies the verified EF provider version, not the UO.Analyzers package version.

`ef_core_providers` is a comma-separated, case-insensitive list. Whitespace and duplicate entries are
accepted. There is no default provider. Unknown entries are ignored; if none are recognized, there
is no diagnostic. An unknown entry does not establish support or appear in the warning.
Runtime `UseNpgsql` / `UseSqlite` calls and package references are not provider selectors.
Selecting both profiles reports one diagnostic naming all selected profiles for which the overload
is known to be unsupported.

`assume_ef_core_queryable` defaults to `false`. Set it to `true` only where unknown `IQueryable<T>`
parameters, fields, properties, method results or awaited results represent EF queries. This supports
ABP `GetQueryableAsync()` and helpers receiving repository queries without referencing ABP in the analyzer.
Scope it narrowly: this is a user assertion, so an unrelated provider passed into an opted-in helper
will also be treated as EF. Merely referencing EF does not assert anything about opaque queryables.
Known materialization boundaries and locals with unproven writes are not overridden by opt-in.

### Example: a helper receiving IQueryable

```csharp
private static IQueryable<Customer> ApplyFilters(
    IQueryable<Customer> query, string searchTerm)
{
    var lowerSearchTerm = searchTerm.Trim().ToLowerInvariant();

    return query.Where(customer => customer.NameSurname.Contains(
        lowerSearchTerm, StringComparison.CurrentCultureIgnoreCase));
}
```

With both settings applied to this file, UO0001 marks the `Contains` invocation. The
`ToLowerInvariant()` call on `searchTerm` runs outside the predicate and is not flagged.
Without `assume_ef_core_queryable = true`, the analyzer cannot establish that the `query` parameter
belongs to EF and does not report the call.

### No warning appears

Check these in order:

1. The package is referenced by the project that compiles the source file.
2. The effective `.editorconfig` section matches that file and includes a recognized
   `ef_core_providers` value. Missing or unknown profiles produce no diagnostics.
3. For an opaque `IQueryable<T>` source, `assume_ef_core_queryable = true` applies to the file
   containing the predicate, not just the file calling the helper.
4. A more specific configuration does not disable UO0001 or override its required options.
5. The invocation is row-dependent and falls within the supported predicate and overload scope below.

Rebuild the consuming project to check compiler output as well as the editor. If the build reports
UO0001 but the editor does not, check the IDE's analyzer support and diagnostics filters.

## Verified negative matrix

Reviewed against the **v8.0.0 source tags** on 2026-10-04. The profile names intentionally pin a
single package version, not all 8.x or future releases. Revalidate before applying this snapshot to
another version. Profiles assume stock translators; custom method translators, model mappings and
provider plugins may change the result and are outside this rule's knowledge.

| Exact method signature | Npgsql.EntityFrameworkCore.PostgreSQL 8.0.0 | Microsoft.EntityFrameworkCore.Sqlite 8.0.0 |
| --- | --- | --- |
| `string.ToLowerInvariant()` | Unsupported | Unsupported |
| `string.ToUpperInvariant()` | Unsupported | Unsupported |
| `string.ToLower(CultureInfo)` | Unsupported | Unsupported |
| `string.ToUpper(CultureInfo)` | Unsupported | Unsupported |
| `string.Contains(string, StringComparison)` | Unsupported | Unsupported |
| `string.StartsWith(string, StringComparison)` | Unsupported | Unsupported |
| `string.EndsWith(string, StringComparison)` | Unsupported | Unsupported |
| `string.Equals(string, StringComparison)` (instance) | Unsupported | Unsupported |
| `string.Equals(string, string, StringComparison)` (static) | Unsupported | Unsupported |

The `CultureInfo` and `StringComparison` values do not change these signature-level results.
Nullable reference annotations do not create different CLR overloads.

Evidence for the negative entries is the **absence of a matching signature in the stock translation
paths**, not just absence from a documentation table:

- Npgsql's [string translator](https://github.com/npgsql/efcore.pg/blob/v8.0.0/src/EFCore.PG/Query/ExpressionTranslators/Internal/NpgsqlStringMethodTranslator.cs)
  matches only the parameterless `ToLower` / `ToUpper`; its
  [SQL visitor](https://github.com/npgsql/efcore.pg/blob/v8.0.0/src/EFCore.PG/Query/Internal/NpgsqlSqlTranslatingExpressionVisitor.cs)
  matches the single-string `Contains`, `StartsWith`, and `EndsWith` overloads.
- SQLite's [string translator](https://github.com/dotnet/efcore/blob/v8.0.0/src/EFCore.Sqlite.Core/Query/Internal/SqliteStringMethodTranslator.cs)
  matches parameterless casing and single-string `Contains`; its
  [SQL visitor](https://github.com/dotnet/efcore/blob/v8.0.0/src/EFCore.Sqlite.Core/Query/Internal/SqliteSqlTranslatingExpressionVisitor.cs)
  handles single-string `StartsWith` and `EndsWith`.
- The shared [Equals translator](https://github.com/dotnet/efcore/blob/v8.0.0/src/EFCore.Relational/Query/Internal/EqualsTranslator.cs)
  accepts the instance one-argument and static two-argument shapes. The
  [relational SQL visitor](https://github.com/dotnet/efcore/blob/v8.0.0/src/EFCore.Relational/Query/RelationalSqlTranslatingExpressionVisitor.cs)
  explicitly identifies the two `StringComparison` equality overloads as translation failures.
- Translator registration was checked in the [Npgsql provider](https://github.com/npgsql/efcore.pg/blob/v8.0.0/src/EFCore.PG/Query/ExpressionTranslators/Internal/NpgsqlMethodCallTranslatorProvider.cs),
  [SQLite provider](https://github.com/dotnet/efcore/blob/v8.0.0/src/EFCore.Sqlite.Core/Query/Internal/SqliteMethodCallTranslatorProvider.cs), and
  [relational provider](https://github.com/dotnet/efcore/blob/v8.0.0/src/EFCore.Relational/Query/RelationalMethodCallTranslatorProvider.cs).

The live [Npgsql mapping table](https://www.npgsql.org/efcore/mapping/translations.html) and
[SQLite mapping table](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/functions) are useful
references but evolve independently of these pinned profiles. No warning for another overload means
**not covered by the negative catalog**, not a guarantee of SQL translation.

## Query context and row dependency

Supported contexts are the exact, non-indexed `Queryable` predicate overloads with two parameters,
whose second parameter is `Expression<Func<TSource, bool>>`:
`Where`, `Any`, `All`, `Count`, `LongCount`, `First`, `FirstOrDefault`, `Single`, `SingleOrDefault`,
`Last`, and `LastOrDefault`. Overloads with explicit default values are not included.

Known sources are real EF `DbSet<T>` (including `DbContext.Set<T>()` results), `DbSet.AsQueryable()`,
and query chains preserving those sources through `Queryable` and EF query extensions such as
`AsNoTracking`. Local initializer aliases are traced within the operation block, including locals
reassigned only through query chains rooted in themselves (`query = query.Where(...)`). Such
composition preserves the original source through conditional statements, loops and closures.
Properties/fields of opaque `IQueryable<T>` are not traced through their implementations.
The source follows the argument's parameter symbol, including reordered named arguments.

For example, with a recognized provider profile and repository opt-in configured:

```csharp
var query = await employeeRepository.GetQueryableAsync().ConfigureAwait(false);
if (!string.IsNullOrWhiteSpace(input.Filter))
{
    var filter = input.Filter.Trim().ToLowerInvariant();
    // Warning on Contains, even though query is reassigned.
    query = query.Where(x => x.FirstName.Contains(filter, StringComparison.InvariantCultureIgnoreCase));
}
if (input.IsActive is { } isActive)
    query = query.Where(x => x.IsActive == isActive);
```

```csharp
// Warning on ToLowerInvariant: depends on the SQL row.
db.Customers.Where(x => x.Name.ToLowerInvariant() == term);

// No warning: captured value can be evaluated independently of the row.
db.Customers.Where(x => x.Name.ToLower().Contains(term.ToLowerInvariant()));

// Both x and y are recognized query parameters in the inner predicate.
db.Customers.Where(x => db.Customers.Any(y =>
    x.Name.Equals(y.Name, StringComparison.OrdinalIgnoreCase)));
```

Conversions and nullable annotations preserve row dependency. Constants (including `nameof`)
do not become row-dependent just because their syntax mentions a lambda parameter.
Calls on ordinary captured/local values are not marked. Each enclosing lambda must be recognized
before its parameters can contribute; analysis does not assume arbitrary nested delegates execute as SQL.

## Boundaries and intentional gaps

- `Enumerable` operations and their materialized results stop source tracing, including a subsequent
  `AsQueryable()`. A `ToList()` elsewhere in a method has no effect on another query chain.
- No `Select` body is analyzed in this version, even an intermediate projection used by a later filter.
  Its later `Where` predicate can still be analyzed. This avoids treating final projections as guaranteed
  SQL work: EF permits [client evaluation in the final projection](https://learn.microsoft.com/en-us/ef/core/querying/client-eval).
- Ordering, grouping, joins, `SelectMany`, EF async terminal predicates, indexed predicates,
  navigation-collection `Enumerable` predicates and expression trees stored in variables are not analyzed.
  Nested/correlated inline predicates on proven EF sources are supported; arbitrary expression composition is not.
- Local writes other than self-rooted query composition, `ref`/`out` escapes, conditional query sources
  and interprocedural provenance are conservatively skipped. An unproven write invalidates the local
  for the entire block, even before that write. There is no path-sensitive or cross-method data-flow analysis.
- Row dependency follows the operation subtree, not user method bodies or mutable captured state.
  Unknown calls are not catalogued as unsupported. This is not a complete EF translator or query validator.
- Generated code is skipped. Missing/malformed bindings are ignored; cancellation and concurrent execution
  are supported. Symbols are resolved once per compilation; local initializer/write information once per block.

Choose provider-supported operations and database/column collations that preserve your requirements.
Review [EF collation and case-sensitivity guidance](https://learn.microsoft.com/en-us/ef/core/miscellaneous/collations-and-case-sensitivity)
for culture and index implications. Removing `StringComparison` or swapping invariant casing can change
results, so the analyzer offers no automatic fix and does not propose moving the query to the client.

## Implementation and validation

`UnsupportedEfCoreTranslationAnalyzer` registers callbacks and reports diagnostics.
`QuerySymbols`, `QuerySourceAnalysis` and `QueryContextAnalysis` identify query provenance and predicates.
`LocalQuerySources` gathers aliases whose initializers remain valid evidence of their query provider,
while `RowDependency` checks parameter dependency.
`MethodSignature` resolves exact overloads; `TranslationRules` creates a catalog of immutable
`UnsupportedMethodRule` entries with a common evaluation contract. `ProviderConfiguration` owns options
and profile labels. New signature-only rules do not change the analyzer or context analysis.

Roslyn tests use real EF Core 8.0.0 metadata, test both casing and comparison families, and assert the
ID, warning severity, full invocation span and message arguments. They do not start a database, translate
SQL, or prove live provider acceptance. IDE discovery and runtime acceptance remain separate checks.
